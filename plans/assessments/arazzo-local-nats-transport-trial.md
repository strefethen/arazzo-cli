# Local Core NATS transport trial (2026-10-21)

Ticket: [ac-ee786](https://tkt.stevetrefethen.com/docs/ac-tickets/ac-ee786). This is a test-only result for the later production decision in [ac-eb31c](https://tkt.stevetrefethen.com/docs/ac-tickets/ac-eb31c).

## Contract exercised

The fixture writes real Arazzo 1.1.0 and AsyncAPI 3.0.0 files to an isolated temporary directory. Its three channel keys have distinct literal NATS subjects, unique per invocation. `resolve_local_channel` supplies the source, document, key, pointer, action, and authored address before each send or receive operation. The trial's endpoint comes from the owned local server, not the AsyncAPI document. Rust fixture JSON templates use the existing payload evaluator, and the ordinary Engine scheduler performs explicit `send → receive → forward` dependencies, output publication, success criteria, and message-aware actions.

The Arazzo 1.1.0 text in `spec/arazzo/v1.1.0.html` says channelPath is “A reference to a Source Description Object combined with a JSON Pointer to reference an event channel.” It also says, “For AsyncAPI send operations, the step completes immediately after the message is sent.” and “Arazzo does not model broker acknowledgment or delivery confirmation.” AsyncAPI 3.0.0 channel shape is in `spec/asyncapi/v3.0.0.html`. This trial introduces no document syntax, binding interpretation, payload-authoring rule, or acknowledgment step. A successful NATS `publish`/`flush` is evidence that client output was flushed, not proof of consumer receipt or durable delivery.

## Evidence

- Real broker path: seven explicit debug and release live tests passed, including independent responder receipt of initial `{"order":7}` and observer receipt of forwarded `{"id":42}`. Engine outputs were numeric `42` and string header `reply`; each recorded route had the expected source/document/pointer/action and the authored address. The reply subscriber pump was registered and flushed before the request publish. In the early-reply case the send step had returned and the scheduler entered a fixture receive gate; the pump had already buffered a broker reply, while the receive operation counter was still zero. Releasing the gate consumed that retained reply. This proves the fixed fixture ordering boundary, not a general subscription scheduling policy.
- Completion and failure: message-conditioned `onSuccess` and failed-criterion `onFailure` ended before forward. Malformed JSON and a multi-valued header failed visibly. Invalid/missing channel targets, unsupported requestBody/correlationId, and a wildcard address failed before publish. Changing the authored request address sent to the changed subject and not the original subject. A separate live case buffered a reply from the preregistered subject, changed the local receive address, and proved the full route mismatch failed before the old reply was consumed or any forward occurred. No-reply expiry, cancellation after receive-wait registration, and server termination after registration produced separate markers or `ExecutionCancelled`; no failed case forwarded.
- Cleanup: one live-fixture owner now catches setup, body, assertion, and watchdog failures before bounded teardown. It cancels execution, joins or aborts and awaits spawned responder tasks, joins the trial reply pump, closes each client, and reaps the server. A post-connect invalid subscription proves `NatsTrial::connect` closes a client when setup fails. Injected setup failure after probe subscription and a real reply-buffer watchdog after trial connection both propagate only after teardown; the latter observes a pending task's drop, joined pump, and engine/probe `Closed` events. Successful live cases also observe `Closed` for all clients. In the dead-server case both engine and probe use finite reconnect attempts; async-nats emits `Disconnected` but no `Closed` after reconnect exhaustion, so cleanup requires a rejected `flush` command (`FlushErrorKind::SendError`) as the observable proof that each command handler terminated. A drain timeout alone cannot pass. The receive wait counter returns to zero and its lock is available after every execution result.
- Regression and build: `cargo +1.88.0 check -p arazzo-runtime --tests --locked`, `cargo check --workspace`, `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, and `cargo test --workspace` all exited zero on the final source. Controlled-exchange tests (9), AsyncAPI target tests (8), message-context tests (5), runtime and CLI normal/dry-run fail-closed tests, and the ordinary NATS test filter (2 passed, 7 ignored) passed. The explicit serial live debug and release invocations each executed all seven tests and passed (7/7). Final logs are `/private/tmp/ac-ee786-evidence/review-fix-{msrv-check,check-workspace,fmt,clippy-workspace,test-workspace,live-debug,live-release}.log`.

The live trial deliberately excludes CLI/MCP/DAP activation, server discovery, declarative payloads, operationId, correlation, whole-step timeout semantics, retries, durability, authentication, TLS, JetStream, and a production subscription policy. Core NATS is at-most-once; these local observations do not establish delivery guarantees or production readiness.
