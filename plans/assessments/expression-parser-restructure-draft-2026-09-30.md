### DEC-2: Condition syntax (ac-ec3a1 rows 1–6)

The spec fixes the literals (§5.8.11.1), the operator list (§5.8.11.2: `< <= > >= == != ! && || () [] .`,
where `[]` is "Index (0-based)" and `.` is "Property de-reference"), and the exclusion of `contains`,
`matches` and `in`. Everything else below is a maintainer-selected interpretation, except row 6, which
the spec settles. The spike's `cond.pest` implements every row, and the examples are the spike's
observed results.

| Row | Proposal | Accept | Reject |
|---|---|---|---|
| 1 Whitespace | Optional space, tab, CR, or LF around operators and inside `()` and `[]`. Never inside an operand, number, keyword, or two-character operator | `$statusCode==200`, `( $statusCode == 200 )` | `$statusCode = = 200` |
| 2 Precedence | `\|\|` below `&&` below comparison below postfix. `&&` and `\|\|` are n-ary, left to right. Comparisons don't chain. `!` takes exactly one postfix operand (a group counts) and cannot be followed by a comparison operator | `A && B \|\| C` = `(A && B) \|\| C`; `!(A == B)`; `!A && B` | `!A == B`, `A == B == C`, `!!A`, `!` |
| 3 Operand boundary | Deterministic, so no ambiguity error. Inside a condition, the four unbounded operand terminals (query/path `name`, header `token`, JSON Pointer reference tokens, source-reference id) stop before whitespace or any of `= ! < > & \| ( ) ' [ ]`. As a result, `ConditionErrorKind::AmbiguousRuntimeExpressionBoundary` is removed. Names containing those characters can't be referenced from a simple condition | `$request.query.x==true`; `$response.header.X\|\|$inputs.y` | `$response.header.X\|\|Y` (`Y` is a bare word) |
| 4 `.` syntax | `.` followed by `[A-Za-z0-9_-]+`, chainable, on any operand. Identifiers are greedy (plan line 179), so after `$inputs.x`, `$outputs.x` and step outputs the dot belongs to the name. Postfix `.` therefore follows `$request.body`, `$response.body`, `$message.payload`, groups, and other forms that don't end in a name. Semantics stay with ac-ec3a1 | `$response.body.items[0].id` | `$response.body.` |
| 5 `[]` syntax | `[` non-negative integer, no sign, no leading zero `]`, chainable. Semantics stay with ac-ec3a1 | `[0]`, `[12]` | `[-1]`, `[01]`, `['a']`, `[]` |
| 6 Numbers | **Settled by spec.** §5.8.11.1 says "Any number format supported in Data Types", and §5.4 bases those on JSON Schema types, so a number literal is a JSON (RFC 8259) number | `200`, `-1`, `2.5`, `2e2` | `+200`, `0200`, `.5`, `5.` |
| Literals | `true`, `false`, `null` in lowercase, not followed by an identifier character. Strings are single-quoted with `''` as the escape and no other escapes (a backslash is literal) | `'It''s'`; `'a\' != 'a\'` is two literals | `"apple"`, `$x contains 'a'`, `$x in [1]` |

Spike results on these rules: 45 of 53 corpus conditions parse; the 8 rejections are exactly the
non-spec forms (double quotes, `contains`, `in [...]`, and the pinned `"just a string"`). All 59
condition operands also parse as standalone expressions.

### DEC-3: Keyword case in runtime expressions

- **Background:** ABNF quoted strings are case-insensitive (RFC 5234 §2.3). Read literally, the spec
  accepts `$STATUSCODE`, `$Inputs.x`, and `$response.HEADER.x`.
- **Proposal:** follow the ABNF. It is conformant and costs nothing, because the generator already
  emits `^"…"`. Names and IDs stay case-sensitive values.
- **Alternative:** case-sensitive keywords. That rejects spec-valid input, so it would need a
  manifest `deviation` entry.

### DEC-4: Condition nesting limit (I2)

- **Proposal:** before pest runs, a linear scan counts `(` and `!` depth outside single-quoted
  strings. Depth above **32** returns the existing frozen `ConditionErrorKind::NestingLimit`.
  Tests cover depth 32 and 33 only; nothing tests thousands of levels.
- **Why this is needed:** pest recursion isn't bounded by depth. In the spike, a debug build
  overflowed a 2 MiB stack at 300 nested parens. `pest::set_call_limit` counts total rule calls, not
  depth, and a flat 50-term `&&` chain already exceeds a 3000-call budget.
- **Audit I2:** mark it "owned by ac-67bf5 (NestingLimit 32)". It drives nothing else.

### DEC-5: Dotted `$response.body.x` outside simple conditions (new decision ticket, not decided here)

- **The spec contradicts itself:**
  - The §5.9 ABNF allows only `"body" ["#" json-pointer]`, and every §5.9.1 example uses the
    pointer form (`$response.body#/status`).
  - §5.8.11.3 shows `context: $response.body.status`. `context` is a required-expression field.
- **The accepted plan and tickets would break it:**
  - Plan line 184 says "namespace-specific source forms remain exact".
  - ac-9eaf1 makes `evaluate_with_diagnostics` call `parse_runtime_expression`, and it preserves
    the "invalid-call null-plus-diagnostic contract". A dotted output would therefore evaluate to
    null with a warning.
  - ac-4cd56 rejects it in required-expression fields.
  - In literal-or-expression fields, ac-a48b1's classifier would treat it as a literal string.
- **Blast radius:**
  - sonos-hub: 170 dotted references under `outputs:`, plus 1 in a condition, across 20 provider
    files, alongside 168 pointer references.
  - 43 of 140 expressions in this repo's fixtures.
  - pro-picks: 0 dotted, 78 pointer.
  - The conformance audit's F13 calls the dotted form "the spec's `.` de-reference", which is true
    only inside simple conditions.
  - The fate of `lib.rs`'s hand-written dot-path and filter parser (`tokenize_path`,
    `parse_filter_expr`, F13) depends on this decision.
- **Options:**
  - A. Spec-exact: migrate sonos-hub and the fixtures to `#/` pointers, and correct F13.
  - B. A recorded compatibility deviation, like d1e2f: add a grammar production plus an evaluator
    mapping from `.a.b` to `#/a/b`.
  - C. Warn now, reject later. This is a degraded mode, so it needs your explicit approval under
    the global contract.
- **Correction (2026-09-30):** the spec's dotted examples are not limited to one condition-section
  `context`. The async examples use `orderId: $message.payload.orderId` in Step `outputs` twice.
  Only the §5.9.1 examples table is pointer-exclusive.

- **In-repo blast radius:**
  - `arazzo generate` emits dotted `outputs` (`crud.rs:924-929`).

  - 136 dotted references sit in 34 fixture files, all under `outputs`.
- **The accepted plan already leans toward A.** It removes "any secondary Runtime Expression
  scanners … without a feature flag, fallback, warning-only mode, or extension entry" (§Effective

#### Recommendation: A, spec-exact outside simple conditions

`.member` and `[n]` stay valid inside simple conditions, as DEC-2 already accepts. The reasons:
- The normative grammar and the editor's explicit statement both say pointer-only, and the 1.1.0
  examples reintroduced a form that #260 had removed.
- Every grammar-backed implementation (Redocly, Speakeasy, swaggerexpert, and Jentic's TypeScript
  tools) rejects the form outside conditions. Only Jentic's unvalidated Python runner accepts it.
- Option B would make us the only grammar-based implementation that extends the grammar, and it
  would require inventing semantics (escaping `.`, `~`, and `/` in member names) for a deviation.

A needs these conditions to be safe:
1. **No silent literals or nulls.** Redocly and Jentic's TypeScript runner turn a dotted output into
   a literal string with no error. Ours must surface as a failure naming the fix (for example,
   "use `$response.body#/status`").
2. **Migrate first.** A new Tier 2 ticket migrates the generator (with RFC 6901 escaping of member
   names), README, docs, and the 136 fixture references. ac-9eaf1 depends on it, so evaluation
   switches only after our own artifacts use pointers.
3. **sonos-hub** is migrated in its own repository (170 outputs, a mechanical `.a.b` → `#/a/b`
   rewrite) before it upgrades past ac-9eaf1.
4. **F13 is corrected** in the conformance audit, and an upstream erratum report on the 1.1.0
   examples is drafted for Steve to file (following the ac-d1e2f precedent), possibly as a comment
   on #518.

### 6.1 ac-80673: rewritten body

**Title:** Generate the Runtime Expression parser from the spec ABNF with pest
**Plan:** `plans/current/arazzo-1.1-conformance-evidence.md` (amended 2026-09-30)
**Reads:** `AGENTS.md`, `god-files.md`, `spec/arazzo/v1.1.0.html`, `plans/current/arazzo-1.1-conformance-evidence.md`, `crates/arazzo-expr/src/lib.rs`, `crates/arazzo-expr/Cargo.toml`, `Cargo.lock`
**Writes:** `crates/arazzo-expr/Cargo.toml`, `crates/arazzo-expr/build.rs`, `crates/arazzo-expr/grammar/**`, `crates/arazzo-expr/src/lib.rs`, `crates/arazzo-expr/src/runtime_expression.rs`, `crates/arazzo-expr/tests/runtime_expression_scaling.rs`, `Cargo.lock`

#### Goal

Provide the one Arazzo 1.1 Runtime Expression parser, generated by pest from the vendored spec's
§5.9 ABNF and exposed through the already-frozen borrowed public surface. Its consumers are ac-9eaf1,
ac-a48b1, ac-67bf5, ac-2f84e, and later the validator. Authority is the amended plan §"Runtime
Expression parsing precedes field dispatch" (DEC-1, DEC-3).

#### Design

- **Grammar source:** the ABNF block under §5.9 ("The runtime expression is defined by the following
  ABNF syntax") is committed verbatim as `grammar/arazzo-1.1-runtime-expression.abnf`, with HTML
  tags stripped and entities decoded. A `;` header records the source anchor and the one repair:
  the `expression` rule's closing `)` is indented so RFC 5234 reads it as a continuation.
- **Build:** `build.rs` follows `iregexp-rs`'s `build.rs` at its pinned rev `e22a35b`. It converts
  the ABNF with `abnf_to_pest::parse_abnf` and `render_rules_to_pest`, appends the hand-written
  `grammar/arazzo.pest`, emits the parser into `OUT_DIR` with `#[grammar_inline]`, and declares
  `cargo:rerun-if-changed` for both grammar files.
  Dependencies: `pest = "=2.9.1"` and `pest_derive = "=2.9.1"` in `[dependencies]`, and
  `abnf_to_pest = "=0.6.0"` in `[build-dependencies]`. All of these are already in `Cargo.lock`.
  Package review: *[fill in at rewrite time with the add-package verdict and date]*.
- **Hand-written rules** (`arazzo.pest`) hold only decisions:
  - an entry rule `runtime_expression = { SOI ~ rt_expression ~ EOI }`;
  - `rt_expression`, with namespace-exact source alternatives per plan lines 184–185 and the
    AGENTS.md surface: `$request.` → header/query/path/body; `$response.` → header/query/path/body;
    `$message.` → header/payload. They reuse the generated `*_reference`, identifier, token,
    pointer and CHAR rules. The generated `expression` and `source` rules stay unused, because
    they admit `$message.query` and `$request.payload`.
  - Generated keyword literals stay case-insensitive (DEC-3).
- **Mapping:** `runtime_expression.rs` converts parse pairs into the frozen types through one
  crate-private function. ac-67bf5 will reuse that function for condition operands, so it accepts
  either the standalone or the condition-context variant of each terminal. Greedy dotted
  identifiers, strict step, workflow and source names, and the complete source-reference tail come
  from the grammar; no post-parse re-scanning.
- **Errors:** `Empty` and `MissingDollarPrefix` are detected before parsing.
  - A successful parse of the unanchored `rt_expression` that stops before the end → `TrailingInput`
    over the unconsumed range.

#### Goal

#### Design

- **Grammar:** append the DEC-2 rules to `arazzo.pest` exactly as the table specifies: `condition`,
