Cycle 08 · 28 Oct 2026Model groundwork · reviewed locally

One view of inherited Step parameters

The model now offers one reliable answer to “which parameters apply to this Step, and where were they declared?” Future validation and execution consumers can share that answer across operationId, operationPath, channelPath and workflowId targets. Consumer adoption is still pending.

Before · separate consumer rules

Inheritance was duplicated

Runtime and validation each implement their own merge and currently skip inherited parameters for workflow-target Steps. The model had no common overlay API.

After · shared model API

All four targets share one rule

A Step overrides only the exact name and location pair. Other inherited declarations remain, followed by every Step declaration. Each result points back to its original declaration.

Input declarations · child-workflow Step

Workflow parameters:
  mode: brief
  limit: 10
Step 0 parameters:
  limit: 25

Illustrative values; all three declarations have an absent in. The Step supplies a new value for the same limit identity.

New API result · value and origin

mode: brief  ← Workflow parameter 0
limit: 25    ← Step 0 parameter 0

The new model view retains mode and the Step’s limit. This demonstrates the helper; it is not a claim that the runtime inheritance defect is already fixed.

One responsibility, one small module

arazzo-spec/effective_step.rs owns the borrowed overlay and provenance. The crate root adds module wiring and exports only. Expression parsing, contextual validation, component resolution and execution remain with their existing owners. Duplicate declarations stay visible for validators to diagnose.

A 40-case matrix covers every target and override scenario. Four public API tests plus focused unit proof cover exact names and locations, absent locations, duplicates, ordering, provenance, invalid indexes and rejected nonconformant location spellings. Full workspace: 1,545 passed, 0 failed, 35 ignored. Formatting, compilation, strict Clippy, public API docs and all four drift guards passed.

Cycle 07 · 28 Oct 2026Architecture groundwork · reviewed locally

One owner for finding Step references

Dependency analysis now has a shared syntax API that can distinguish a real Step-output reference from ordinary text. It preserves names, duplicates and source order without evaluating a workflow. Runtime scheduling and validator consumers will adopt it in later slices.

Before · consumers needed their own discovery

Text scans could disagree with parsing

There was no single field-mode adapter for Step references. A dollar sign alone cannot tell a dependency scanner whether text is an operand, a template or a quoted literal.

After · canonical syntax API

Four modes, existing parsers

Literal values, required expressions, simple conditions and embedded typed conditions each use their existing syntax owner. Only a parsed local Step-output reference enters the result.

Simple condition · real operand

$steps.fetch.outputs.ready == true
→ [(fetch, ready)]

The parsed operand names a producer. Quoted '$steps.fetch.outputs.ready' is ordinary string data and contributes no reference.

Typed condition · braces matter

^{$steps.fetch.outputs.code}$
→ [(fetch, code)]

Unbraced dollars and native regex quantifiers remain condition text. A malformed reserved {$…} candidate returns an error and no partial list.

A small owner with a deliberate boundary

step_output_reference.rs owns the field-mode adapter. expression_string.rs shares its existing candidate iterator; the crate root adds exports only. Document traversal, output existence, graph construction and scheduling stay with their respective consumers.

10 public API tests pass. Full workspace: 1,540 passed, 0 failed, 35 ignored. Formatting, compilation, strict Clippy, benchmark compilation, public API documentation and all four drift guards passed. Existing expression classification and typed Criterion rendering retain their behavior.

Independent review PASS · ac-2f84e · Step inheritance and dependency safety epic · source f4c6e48 (local; not pushed). This is a new library capability and groundwork for dependency safety; it does not yet change workflow execution order. Fable’s Kafka/AsyncAPI paths are untouched.

Cycle 06 · 28 Oct 2026Reliability + ownership · reviewed locally

Regex checks retain a bounded cache

Long-lived engines can encounter new regex patterns on every run. The cache now limits what it retains, reuses compilation failures, and releases its map lock before compiling or matching a pattern.

Before · cache inside Criterion evaluation

Every successful pattern stayed

The map grew with distinct patterns. Invalid patterns compiled again on every repeat, and compilation held the lock used by other steps.

After · private cache owner

Retain up to 256 results per engine

Successful and failed compilations share the same bound. A new entry at capacity clears the table before insertion. Hits, compilation and matching preserve the same results.

A retention limit, not a new pattern restriction

Patterns over 4,096 UTF-8 bytes still evaluate normally; their compilation result is not retained. Repeating an eligible pattern reuses the result until eviction. Simultaneous first requests may compile the same pattern more than once.

Cache policy has one home

regex_cache.rs owns retention and locking. criteria.rs keeps Criterion semantics and delegates regex matching. The cache stays private to each engine, with no new dependency or public API.

Same workflow result and evidence

Serial and parallel runs preserve outputs and complete semantic trace records. Invalid patterns retain the same error text. Typed interpolation and existing Criterion tests stay unchanged.

9 cache tests and a real parallel workflow pass in debug and release. The workflow proves three overlapping requests and full semantic trace equality. Full workspace: 1,530 passed, 0 failed, 35 ignored; formatting, compilation, strict Clippy and all four drift guards passed.

Independent review PASS · ac-e81bc · source 7dc80ba (local; not pushed). This cycle proves cache bounds, reuse and lock discipline; it makes no throughput claim. Fable’s Kafka/AsyncAPI work remains untouched.

Cycle 05 · 28 Oct 2026Validation fix · reviewed locally

Versions are checked before a workflow runs

A typo or unsupported feature set now produces a clear validation error at arazzo. Patch releases within the supported 1.0 and 1.1 feature sets remain compatible, and the declared version text is preserved.

Before · prefix-only check

Starting with “1.” was enough

arazzo: "1.foo.0" and arazzo: "1.2.0" passed the top-level version check.

After · syntax and feature set

Validate all three decimal components

1.foo.0 fails as malformed. 1.2.0 fails as unsupported. Both use the existing unsupportedVersion diagnostic at arazzo.

Patch compatibility stays intact

1.0.27 and 1.1.27 are accepted. Patch components are not limited by a machine integer. Decimal spellings with leading zeros use the same feature comparison, without rewriting the document.

The same classifier protects vocabulary rules: 1.0 still rejects querystring and action Parameters; 1.1 permits them. An incomplete 1.0 declaration cannot select a feature set.

One private owner

version.rs owns syntax, supported feature sets and vocabulary classification. The validator facade delegates and shrinks from 2,933 to 2,916 lines; its enforced cap is lowered.

A deliberately bounded delivery

Source URL validation and optional source-type handling remain separate work. Fable’s Kafka/AsyncAPI paths and CLI/MCP output schemas are unchanged.

6 focused tests passed across YAML, JSON and direct validation. Five fail on the old implementation; the required-field control stays green. Full workspace: 1,520 passed, 0 failed, 35 ignored; formatting, compilation, strict Clippy and all four drift guards passed.

Cycle 04 · 28 Oct 2026Capability + correctness · reviewed locally

Success checks can use workflow values

Use inputs and earlier step outputs inside regex, JSONPath and explicit XPath 1.0 conditions. One workflow can check the expected value for each run instead of hard-coding it into every condition.

Before

Embedded expressions stayed unresolved

Typed conditions reached their evaluator with the original {$inputs.expectedStatus} text still embedded.

After

Substitute first, then evaluate

The existing expression renderer supplies the value, then the selected condition engine evaluates the completed string. An unresolved or malformed substitution fails the check. Values use the existing string conversion; authors still supply any quoting required by the target language.

Example: expected status comes from an input

For expectedStatus: ready and JSONPath context $response.body:

$[?(@.status == "{$inputs.expectedStatus}")]

evaluates as $[?(@.status == "ready")]. A matching response item passes; no matching item fails.

Missing data cannot pass an empty regex

Null or missing context fails all three typed checks. In particular, ^$ cannot pass because missing data was converted into an empty string.

Existing boundaries remain intact

Native dollar syntax and simple conditions keep their semantics. JSONPath admission errors remain visible with missing context. Traces retain the declared condition, and unsupported XPath versions remain unsupported.

9 focused tests passed. Seven of the initial eight regression tests fail on the old implementation; the compatibility control stays green. Full workspace: 1,514 passed, 0 failed, 35 ignored; formatting, compilation, strict Clippy and all four drift guards passed.

The existing runtime.typed-criterion-interpolation-and-null claim is now covered by positive and negative executable evidence. The change reuses the canonical renderer inside the existing Criterion owner, with no new parser, public field or God-module expansion.

Independent review PASS · ac-50846 · source be884e2 (local; not pushed). Publication is held because main also contains Fable’s paused conformance candidate; its review gate remains intact.

Cycle 01 · 28 Oct 2026Two fixes · completed

Safer execution, safer evidence

A timed-out test cannot unlock its dependent

Your test suite now preserves the meaning of incomplete work. Timed-out and cancelled cases do not enter the completed-workflow set.

Before

Case A times out → recorded as completed → dependent B runs.

After

Case A times out → remains incomplete → dependent B is refused before sending a request.

A retains RUNTIME_EXECUTION_TIMEOUT. B reports RUNTIME_WORKFLOW_DEPENDENCY_UNSATISFIED. Passing cases and ordinary failures retain their existing completion semantics.

Hermetic HTTP request log proves B sends no request; regression fails on the pre-change binary. Four focused tests pass. Independent review PASS · pushed · ac-9cc68 · bd00935

Diagnostic URLs redact the whole credential

Persisted traces, redirect-hop URLs and MCP dry-run output no longer expose URL userinfo. The same rule covers a password, a token in the username slot, and multiple raw @ characters.

Before · synthetic example

https://demo:sample@api.example.com/items

After

https://[REDACTED]@api.example.com/items

The bounded edit avoids URL normalization. URLs without userinfo keep their existing bytes; existing sensitive-query redaction continues. Non-loopback cleartext requests with URL credentials now trigger the transport warning.

Tests inspect persisted trace bytes, redirect fields and the MCP protocol response. Existing redaction behavior and trace schema stay stable. Cumulative independent review PASS after a multiple-@ correction · pushed · ac-d95a9 · f9abdd0 + f3cfd10
