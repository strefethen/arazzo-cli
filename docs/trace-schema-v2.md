# Trace Schema v2

`trace.v2` is the on-disk execution trace format generated by:

```bash
arazzo-cli --json run <spec> <workflow-id> --trace <path>
```

and read by `arazzo-cli replay <path>`. The JSON Schema is
[`schemas/trace-v2.schema.json`](schemas/trace-v2.schema.json).

## Top-level object

- `schemaVersion` (string): must be `"trace.v2"`
- `tool` (object): emitting tool metadata
- `run` (object): run-level metadata and status
- `inputs` (object): sanitized JSON workflow inputs
- `inputBlobs` (object, optional): bytes inputs, keyed by input name, each a
  [bytes descriptor](#bytes-descriptor). A bytes input appears here and not in
  `inputs`.
- `steps` (array): ordered step attempt records

## `tool`

- `name` (string)
- `version` (string)

## `run`

- `specPath` (string)
- `workflowId` (string)
- `parallel` (boolean)
- `dryRun` (boolean)
- `timeoutMs` (number)
- `startedAt` (RFC3339 string)
- `finishedAt` (RFC3339 string)
- `durationMs` (number)
- `status` (string: `success` or `failure`)
- `error` (string, optional on failure)
- `transportWarnings` (array, optional): degraded transport-trust facts
- `sequentialFallbacks` (array, optional): workflows that ran their steps one at a time although `parallel` is `true`, one entry per workflow and reason
  - `workflowId` (string)
  - `reason` (string: `controlFlowAction`, `retryReference`, `subWorkflowStep`, `debugger`, or `singleStep`)
  - `stepId` (string, optional): the step that requires sequential execution
  - `message` (string): the explanation `run --verbose` prints

## `steps[*]`

- `seq` (number): deterministic per-run sequence
- `workflowId` (string)
- `stepId` (string)
- `attempt` (number)
- `kind` (string: `http`, `workflow`, or `asyncapi`)
- `operationPath` (string, optional)
- `workflowIdRef` (string, optional)
- `durationMs` (number)
- `request` (object, optional): see below
- `response` (object, optional): see below
- `criteria` (array, optional)
- `decision` (object)
- `outputs` (object, optional): JSON step outputs
- `outputBlobs` (object, optional): bytes step outputs, keyed by output name,
  each a bytes descriptor. A bytes output appears here and not in `outputs`.
- `error` (string, optional)
- `message` (object, optional): the message an AsyncAPI receive step consumed — `transport` (`kafka`), `host`, `topic`, `partition`, `offset`, `timestampMs`, `key` (optional), `headers` (optional), `payloadBytes`, `payloadPreview`/`payload` (optional, redacted and truncated like response bodies), `payloadLossy`, `simulated` (true for a dry run, which evaluates an empty object instead of receiving), `correlationId` (optional resolved expected text, also recorded in dry run), `skippedRecords` (nonnegative integer count of non-matching records before this message, omitted when zero). Absent for HTTP and workflow steps.

## `steps[*].request`

- `method` (string)
- `url` (string): redacted
- `headers` (object, optional): redacted by header name
- `body` (any, optional): the logical request body, redacted by JSON key
- `bodyBlobs` (object, optional): bytes in the request body, keyed by JSON
  Pointer into `body`, each a bytes descriptor. `""` is a whole-body blob;
  `/<name>` is a `multipart/form-data` part.
- `redirects` (array, optional): `{statusCode, from, to}` hops, oldest first

## `steps[*].response`

- `statusCode` (integer)
- `mediaType` (string, optional): the parsed `Content-Type`, essence and
  parameters, for example `text/plain;charset=iso-8859-1`. Absent when the
  response has no `Content-Type` or it does not parse.
- `headers` (object, optional): redacted by header name
- `bodyBytes` (integer): body size as received, after transport content
  decoding
- `body` (string, optional): a JSON or text body as decoded Unicode text,
  whatever its charset. JSON bodies are redacted by key and other text by
  pattern, then truncated to `--trace-max-body-bytes` with a `...` marker.
- `bodyBlob` (bytes descriptor, optional): a bytes body, or a JSON or text
  body that failed to decode. Its content is never recorded.
- `bodyError` (string, optional): why a JSON or text body failed to decode;
  present only with `bodyBlob`.

`body` and `bodyBlob` never appear together. An empty body has neither.

## Bytes descriptor

Bytes are never written to a trace. Wherever a trace records bytes it records
this descriptor instead:

```json
{"kind": "bytes", "size": 5120, "sha256": "<64 lowercase hex digits>", "mediaType": "image/png", "filename": "photo.png"}
```

`mediaType` and `filename` are optional. For a response body, `mediaType` is
the essence of the response's `Content-Type`, without parameters. Bytes from an input declared
sensitive render as the fixed marker `{"kind": "bytes", "redacted": true}`,
with no size and no hash.

Blob slots are marked out of band, by `inputBlobs`, `outputBlobs`,
`request.bodyBlobs` and `response.bodyBlob`. A value elsewhere in the trace
that merely has the descriptor's shape is ordinary JSON, not bytes.

This release records `response.bodyBlob`. `inputBlobs`, `outputBlobs` and
`request.bodyBlobs` are part of the schema now so it does not change when
bytes inputs, outputs and multipart requests arrive.

## Replay

Replay injects each recorded response instead of sending the request. It
rebuilds a `body` from its text by `mediaType` (JSON is parsed; text and XML
stay a string), without applying the `charset` again. A `bodyBlob` replays as
a bytes body, which no expression can read yet; a recorded `bodyError` is
reported as the reason. Replay is as faithful as the recorded trace:
redaction and truncation can change what a later step sees.

## Migrating from `trace.v1`

`replay` refuses a `trace.v1` file with `REPLAY_TRACE_LOAD`, naming both
versions. There is no converter: v1 stored non-UTF-8 bodies lossily, so a v1
body cannot be turned back into what the server sent. Re-record the trace with
`run --trace`.

| `trace.v1` response field | `trace.v2` |
|---|---|
| `contentType` (`json`, `xml`, or the lowercased header) | `mediaType`, the parsed `Content-Type`, absent when there is none |
| `body` (UTF-8, lossily decoded) | `body`, exactly decoded text, for JSON and text bodies only |
| `bodyPreview` | removed; `body` already carries the truncated text |
| `bodyLossy` | removed; decoding is exact or the body becomes `bodyBlob` plus `bodyError` |
| — | `bodyBlob`, `bodyError` |

Every other field keeps its v1 meaning. [`trace-schema-v1.md`](trace-schema-v1.md)
remains as the record of the old format.

## Compatibility guarantees

1. `schemaVersion` is the compatibility gate.
2. Existing fields keep meaning and type within `trace.v2`.
3. New fields may be added (forward-compatible).
4. Breaking changes require a new schema version.
